expirely prints this report when `--json` is set or stdout is not a terminal. This is the output of `expirely tls --json expired.badssl.com`:

```json

  "scanned_at": "2026-11-26T23:13:59.39399Z",
  "warn_days": 30,
  "summary": { "error": 0, "expired": 1, "expiring": 0, "ok": 0, "revoked": 0, "total": 1, "unknown": 0 },
  "filter": { "status": ["expired", "revoked", "expiring", "error", "unknown", "ok"], "limit": null },
  "matched": 1,
  "truncated": false,
  "unreadable": [],
  "results": [
    {
      "kind": "tls_certificate",
      "source": "endpoint",
      "target": "expired.badssl.com:443",
      "status": "expired",
      "days_left": -4246,
      "expires_at": "2015-04-12T23:59:59Z",
      "error": null,
      "tls": {
        "trusted": false,
        "trust_issue": "expired",
        "verify_error": "x509: certificate has expired or is not yet valid: “*.badssl.com” certificate is expired",
        "leaf": {
          "subject": "CN=*.badssl.com,OU=Domain Control Validated+OU=PositiveSSL Wildcard",
          "issuer": "CN=COMODO RSA Domain Validation Secure Server CA,O=COMODO CA Limited,L=Salford,ST=Greater Manchester,C=GB",

          "not_before": "2015-04-09T00:00:00Z",
```

## Report

| Field | Meaning |
|---|---|
| `schema_version` | The version of this format, `2`. It changes when a field is removed or changes meaning, or when a `status` value is added; adding a field keeps it. [Schema 1](#from-schema-1) lists what changed |
| `scanned_at` | When the scan ran, RFC 3339 in UTC |
| `warn_days` | The `--warn-days` value used |
| `summary` | Count of every result per status, `ok`, `expiring`, `revoked`, `expired`, `error` and `unknown`, and their `total`. Filters never change it |
| `filter` | What the report shows: `status`, the statuses shown, most urgent first, and `limit`, the `--limit` value or `null` |
| `matched` | How many results have a status in `filter.status`, before `--limit` |
| `truncated` | `true` when `--limit` left out some of the `matched` results; always present |
| `unreadable` | Places a cloud command could not read, as `source:location` such as `compute:us-east7` or `acm:ap-south-1`, so `results` may lack certificates kept there. Empty when the report is complete, and always empty for a scan of targets. A non-empty list makes the run exit `3` unless a result already makes it exit `1` |
| `results` | The results shown, most urgent first |

The counts come before `results`, so a reader that sees only the start of a long report, as an agent shown the head of a command's output does, still knows how many results there are and whether it has them all.

## Show less

Three flags, on `expirely tls`, `expirely tls aws` and `expirely tls gcp`, shrink what the report shows. None of them changes `summary` or the exit code: a certificate that expired fails the run even when `--status ok` hides it.

| Flag | Effect |
|---|---|
| `--status LIST` | Shows only results with these statuses. `all` shows every status, the default. A declared [AI agent](/agents) that passes no `--status` gets every status but `ok` |
| `--limit N` | Shows at most `N` of the matched results, the most urgent ones; `truncated` says whether any were left out |
| `--fields LIST` | Keeps only these top-level keys in each result, in the order below, with `target` always first. A key the result has no value for, such as `acm` on a scanned target, is `null`. `--fields tls` keeps the whole `tls` object; its `chain` still needs `--details`. It needs JSON output |

Lists take commas, a repeated flag, or both: `--status expired,expiring` is `--status expired --status expiring`. Every value is checked before the first connection, and an unknown status or field exits `2` with `invalid_flag`, naming the valid ones.

Results are always sorted the same way, in JSON and in text: by status, `expired`, `revoked`, `expiring`, `error`, `unknown`, `ok`; then a certificate in use before one nothing uses, for `expirely tls aws` and `expirely tls gcp`; then fewest `days_left`, with unknown days last; then in the order they came. In text, a last line such as `showing 7 of 240 (--status expired,expiring; --limit 20)` says what was left out.

```sh
expirely tls -f targets.txt --status expired,expiring --fields status,days_left --limit 20
```

## Result

A field that could not be read is `null`, never zero or a default date. Every result has the same common fields, whatever its kind; what only one kind or one source has lives in its own object.

| Field | Meaning |
|---|---|
| `kind` | The kind of resource: `tls_certificate` for every command today |
| `source` | Where the result was read: `endpoint` for `expirely tls`, `aws_acm` for `expirely tls aws`, `gcp` for `expirely tls gcp` |
| `target` | `host:port` as scanned, or the certificate's domain for a cloud source |
| `status` | `ok`, `expiring`, `revoked`, `expired`, `error` or `unknown` |
| `days_left` | Whole days until `expires_at`, negative once expired; `null` on error or when unknown |
| `expires_at` | When the resource stops working: for a chain, its earliest `NotAfter`; `null` on error or when unknown |
| `error` | `{"code","reason","message","remediation"}` when the target could not be read; `null` otherwise |
| `tls` | What the handshake revealed, described below. Its fields are `null` on error and for a cloud source, which does not verify the chain for a host |
| `acm` | For `expirely tls aws` only: what ACM says about the certificate, described in [expirely tls aws](/cli/tls-aws); absent for other sources |
| `gcp` | For `expirely tls gcp` only: what Google Cloud says about the certificate, described in [expirely tls gcp](/cli/tls-gcp); absent for other sources |

## Status

| Status | Meaning | Exit |
|---|---|---|
| `expired` | `expires_at` has passed | `1` |
| `revoked` | Its CA or provider revoked it, and it has not expired. From `expirely tls --revocation`, or from ACM's own status | `1` |
| `expiring` | `expires_at` is within `--warn-days` | `1` |
| `error` | The target could not be read; `error` says why | `3` |
| `unknown` | The resource exists, but its end date could not be read | `3` |
| `ok` | `expires_at` is later than `--warn-days` | `0` |

`1` wins over `3`. A new status value raises `schema_version`, so a reader that handles every value of its version is never surprised.

## TLS

| Field | Meaning |
|---|---|
| `tls.trusted` | Whether the chain verifies for the host against the system roots |
| `tls.trust_issue` | Why the chain does not verify, as one of the values below; `null` when it does |
| `tls.verify_error` | The full verification error; `null` when the chain verifies |
| `tls.revocation` | With `--revocation`, `{"status","reason"}`: `status` is `good`, `revoked` or `unknown`, and `reason` says when the certificate was revoked or why the state is unknown, `null` when good. A `revoked` certificate that has not expired has the status `revoked`; a chain that does not verify is `unknown` and its CRL is not fetched. `null` when revocation was not checked, which is the default and always the case for a cloud source. See [Revocation](/cli/tls#revocation) |
| `tls.leaf` | The leaf certificate |
| `tls.chain` | Every certificate the server sent, leaf first. Present only with `--details` |

## Trust issues

| Value | Meaning |
|---|---|
| `expired` | A certificate in the chain is outside its validity period |
| `self_signed` | The leaf certificate signed itself |
| `unknown_authority` | The chain does not lead to a root the system trusts |
| `name_mismatch` | The certificate is not valid for the host that was scanned |
| `invalid` | Another verification failure; `verify_error` has the detail |

## Errors of a result

`error.code` is `dial_failed` or `handshake_failed`, listed in [Error codes](/reference/error-codes). `error.reason` says why in a few words, such as `connection refused`, `no such host`, `timed out`, `not a TLS server` or `no certificate sent`; it is for people and can change. `error.message` is the full error. `error.remediation` says what resolves it.

## Certificate

`tls.leaf` and each entry of `tls.chain` have these fields. The chain is most of a report's size, so it is left out unless `--details` asks for it:

| Field | Meaning |
|---|---|
| `subject` | Distinguished name |
| `issuer` | Distinguished name of the issuer |
| `serial` | Serial number in hex |
| `not_before` | Start of validity, RFC 3339 in UTC |
| `not_after` | End of validity, RFC 3339 in UTC |
| `dns_names` | Subject alternative names of type DNS |

## From schema 1

Schema 2 moved the fields only a TLS certificate has into `tls`, added `kind` and `source`, and added the `unknown` and `revoked` statuses.

| Schema 1 | Schema 2 |
|---|---|
| `.trusted`, `.trust_issue`, `.verify_error`, `.leaf`, `.chain` | `.tls.trusted`, `.tls.trust_issue`, `.tls.verify_error`, `.tls.leaf`, `.tls.chain` |
| `--fields trusted,leaf` | `--fields tls` |
| `--fields chain`, without `--details` | `--fields tls --details` |
| Four statuses | `unknown` added, which exits `3`, and `revoked`, which exits `1` |

`target`, `status`, `days_left`, `expires_at`, `error`, `acm`, `gcp` and every report field other than `schema_version` keep their meaning. A reader that supports both checks `schema_version` first.

## Other output

`--version` prints `{"version":"..."}`. A command error prints one line on stderr, the error envelope:

```json
{"error":{"code":"invalid_flag","message":"unknown flag --nope","remediation":"Each command lists every flag and the values it accepts in its --help."}}
```

Its codes are in [Error codes](/reference/error-codes).
