expirely prints this report when `--json` is set or stdout is not a terminal. This is the output of `expirely tls --json expired.badssl.com`:

```json
{
  "schema_version": 1,
  "scanned_at": "2026-11-26T23:13:59.39399Z",
  "warn_days": 30,
  "summary": { "error": 0, "expired": 1, "expiring": 0, "ok": 0, "total": 1 },
  "filter": { "status": ["expired", "expiring", "error", "ok"], "limit": null },
  "matched": 1,
  "truncated": false,
  "unreadable": [],
  "results": [
    {
      "target": "expired.badssl.com:443",
      "status": "expired",
      "days_left": -4246,
      "expires_at": "2015-04-12T23:59:59Z",
      "trusted": false,
      "trust_issue": "expired",
      "verify_error": "x509: certificate has expired or is not yet valid: “*.badssl.com” certificate is expired",
      "leaf": {
        "subject": "CN=*.badssl.com,OU=Domain Control Validated+OU=PositiveSSL Wildcard",
        "issuer": "CN=COMODO RSA Domain Validation Secure Server CA,O=COMODO CA Limited,L=Salford,ST=Greater Manchester,C=GB",
        "serial": "4ae79549fa9abe3f100f17a478e16909",
        "not_before": "2015-04-09T00:00:00Z",
        "not_after": "2015-04-12T23:59:59Z",
        "dns_names": ["*.badssl.com", "badssl.com"]
      },
      "error": null
    }
  ]
}
```

## Report

| Field | Meaning |
|---|---|
| `schema_version` | The version of this format, `1`. It changes when a field is removed or changes meaning, not when one is added |
| `scanned_at` | When the scan ran, RFC 3339 in UTC |
| `warn_days` | The `--warn-days` value used |
| `summary` | Count of every result per status, `ok`, `expiring`, `expired` and `error`, and their `total`. Filters never change it |
| `filter` | What the report shows: `status`, the statuses shown, most urgent first, and `limit`, the `--limit` value or `null` |
| `matched` | How many results have a status in `filter.status`, before `--limit` |
| `truncated` | `true` when `--limit` left out some of the `matched` results; always present |
| `unreadable` | Places a cloud command could not read, as `source:location` such as `compute:us-east7` or `acm:ap-south-1`, so `results` may lack certificates kept there. Empty when the report is complete, and always empty for a scan of targets. A non-empty list makes the run exit `3` unless a result already makes it exit `1` |
| `results` | The results shown, most urgent first |

The counts come before `results`, so a reader that sees only the start of a long report, as an agent shown the head of a command's output does, still knows how many results there are and whether it has them all.

## Show less

Three flags, on `expirely tls`, `expirely tls aws` and `expirely tls gcp`, shrink what the report shows. None of them changes `summary` or the exit code: a certificate that expired fails the run even when `--status ok` hides it.

| Flag | Effect |
|---|---|
| `--status LIST` | Shows only results with these statuses. `all` shows every status, the default. A declared [AI agent](/agents) that passes no `--status` gets `expired,expiring,error` |
| `--limit N` | Shows at most `N` of the matched results, the most urgent ones; `truncated` says whether any were left out |
| `--fields LIST` | Keeps only these keys in each result, in the order below, with `target` always first. A key the result has no value for, such as `acm` on a scanned target, is `null`. `--fields chain` keeps the chain without `--details`. It needs JSON output |

Lists take commas, a repeated flag, or both: `--status expired,expiring` is `--status expired --status expiring`. Every value is checked before the first connection, and an unknown status or field exits `2` with `invalid_flag`, naming the valid ones.

Results are always sorted the same way, in JSON and in text: by status, `expired`, `expiring`, `error`, `ok`; then a certificate in use before one nothing uses, for `expirely tls aws` and `expirely tls gcp`; then fewest `days_left`, with unknown days last; then in the order they came. In text, a last line such as `showing 7 of 240 (--status expired,expiring; --limit 20)` says what was left out.

```sh
expirely tls -f targets.txt --status expired,expiring --fields status,days_left --limit 20
```

## Result

A field that could not be read is `null`, never zero or a default date.

| Field | Meaning |
|---|---|
| `target` | `host:port` as scanned |
| `status` | `ok`, `expiring`, `expired` or `error` |
| `days_left` | Whole days until `expires_at`, negative once expired; `null` on error |
| `expires_at` | The earliest `NotAfter` in the chain; `null` on error |
| `trusted` | Whether the chain verifies for the host against the system roots; `null` on error |
| `trust_issue` | Why the chain does not verify, as one of the values below; `null` when it does or on error |
| `verify_error` | The full verification error; `null` when the chain verifies or on error |
| `leaf` | The leaf certificate; `null` on error |
| `chain` | Every certificate the server sent, leaf first. Present only with `--details`, and `null` on error |
| `error` | `{"code","reason","message","remediation"}` when the target could not be read; `null` otherwise |
| `acm` | For `expirely tls aws` only: what ACM says about the certificate, described in [expirely tls aws](/cli/tls-aws); absent for scanned targets |
| `gcp` | For `expirely tls gcp` only: what Google Cloud says about the certificate, described in [expirely tls gcp](/cli/tls-gcp); absent for scanned targets |

## Trust issues

| Value | Meaning |
|---|---|
| `expired` | A certificate in the chain is outside its validity period |
| `self_signed` | The leaf certificate signed itself |
| `unknown_authority` | The chain does not lead to a root the system trusts |
| `name_mismatch` | The certificate is not valid for the host that was scanned |
| `invalid` | Another verification failure; `verify_error` has the detail |

## Errors of a result

`error.code` is `dial_failed` or `handshake_failed`, listed in [Error codes](/reference/error-codes). `error.reason` says why in a few words, such as `connection refused`, `no such host`, `timed out`, `not a TLS server` or `no certificate sent`; it is for people and can change. `error.message` is the full error. `error.remediation` says what resolves it.

## Certificate

`leaf` and each entry of `chain` have these fields. The chain is most of a report's size, so it is left out unless `--details` asks for it:

| Field | Meaning |
|---|---|
| `subject` | Distinguished name |
| `issuer` | Distinguished name of the issuer |
| `serial` | Serial number in hex |
| `not_before` | Start of validity, RFC 3339 in UTC |
| `not_after` | End of validity, RFC 3339 in UTC |
| `dns_names` | Subject alternative names of type DNS |

## Other output

`--version` prints `{"version":"..."}`. A command error prints one line on stderr, the error envelope:

```json
{"error":{"code":"invalid_flag","message":"unknown flag --nope","remediation":"Each command lists every flag and the values it accepts in its --help."}}
```

Its codes are in [Error codes](/reference/error-codes).
